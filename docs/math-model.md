# Математическая модель crash-раунда

Техническая документация для судей/экспертов — соответствует требованию ТЗ
«обоснование подхода, логика генерации случайных событий и расчёта выигрыша,
параметры модели и влияние настроек на результат». Параметры живут в
`config/game.json`, здесь — их смысл и формулы.

## 1. Точка краха (crash point)

Классическая экспоненциальная модель с house edge, стандарт жанра — легко
объясняется, легко настраивается одним параметром `alpha`, и даёт правильное
распределение (много ранних крахов, редкие "иксы").

```
U = server_rng.uniform(0, 1)          // криптографически стойкий RNG
crash_point = clamp(
  alpha / (1 - U),
  min_crash_multiplier,
  max_multiplier
)
```

- `alpha` (house edge, по умолчанию `0.97`) — чем ниже, тем чаще ранние крахи;
  `1 - alpha` — теоретическое преимущество организатора в долгосрочной серии
  раундов (для бонусной игры без реальных денег это управляет темпом сжигания
  баллов, а не прибылью).
- `min_crash_multiplier` (`1.00`) — минимальный возможный крах, чтобы раунд
  всегда успевал хотя бы стартовать.
- `max_multiplier` (`50.0`) — потолок на случай экстремального `U`, защищает от
  переполнения и от нечитаемых значений на экране.

`U` генерируется на сервере **до** начала полёта и никогда не передаётся клиенту
в явном виде до наступления краха. В обычном раунде seed берётся из
`SecureRandom`, в dev-режиме — из поля `seed` запроса.

**Выбор генератора.** Раунд разыгрывается через `SplittableRandom` (SplitMix64),
а не через `java.util.Random`. Последний построен на линейном конгруэнтном
генераторе, который плохо перемешивает малые seed: первый `nextDouble()` для
seed 1, 2, 3, 7, 42 равен соответственно 0.7309, 0.7311, 0.7311, 0.7307, 0.7276.
То есть все воспроизводимые раунды получали практически одинаковую точку краха
около ×3.6, и dev-режим не давал ничего, кроме иллюзии воспроизводимости.
После перехода на SplitMix64 те же seed дают ×2.24, ×2.37, ×1.09, ×1.59 и ×7.51.
На обычные раунды это не влияло — там seed приходит из `SecureRandom` и заведомо
хорошо распределён.

## 2. Рост коэффициента во времени

Скорость роста сама растёт со временем:

```
r(t) = multiplier_growth_rate * growth_acceleration_base ^ t

multiplier(t) = exp( multiplier_growth_rate * (growth_acceleration_base^t - 1) / ln(growth_acceleration_base) )
```

При `growth_acceleration_base = 1.0` ускорения нет и формула вырождается в
обычную экспоненту `e^(rate * t)` — этот случай считается отдельно, иначе
деление на `ln(1) = 0` даёт бесконечность.

- `multiplier_growth_rate` (`0.06`) — начальная скорость роста.
- `growth_acceleration_base` (`1.12`) — во сколько раз скорость увеличивается
  за секунду полёта.

  Почему не постоянная скорость. При ней приходится выбирать между двумя
  плохими вариантами: либо начало раунда идёт в темпе, где осознанно нажать
  «Забрать» невозможно, либо редкие высокие полёты растягиваются на десятки
  секунд ожидания. Разгон снимает выбор — в начале времени много, к концу
  полёт ускоряется:

  | Коэффициент | Постоянная 0.15 | Разгон 0.06 / 1.12 |
  |---|---|---|
  | 1.10 (первый уровень) | 0.6 с | **1.5 с** |
  | 1.93 (медиана крахов) | 4.4 с | **7.1 с** |
  | 2.50 (сценарий 2) | 6.1 с | **8.9 с** |
  | 10.0 | 15.4 с | 14.8 с |
  | 50.0 (потолок) | 26.1 с | **18.8 с** |

  То есть в зоне принятия решения времени стало в полтора раза больше, а
  хвост, наоборот, сжался с 26 до 19 секунд. Замер на живом сервере совпал с
  расчётом: крах ×3.56 наступил через 11.0 с при предсказанных 10.8 с.

  Темп — продуктовый параметр, а не математический: распределение точки краха
  от него не зависит вообще (медиана остаётся 1.93 при любом темпе), меняется
  только время на решение «забрать или ждать». Для отладки его не трогают, а
  используют dev-поле `speedFactor`.

- `fps` (`10`) и `delta` (`0.1`) — частота тиков WebSocket-события `tick`
  (раз в `delta` секунд), не влияют на саму математику, только на плавность
  отображения. Клиент интерполирует между тиками для 60 fps на экране.
- Раунд завершается (событие `round.finished`), когда `multiplier(t)` достигает
  `crash_point`, вычисленного в п.1.

### Базовый и эффективный коэффициент

В реализации разделены две величины, и это разделение важно понимать:

- **базовый** (`base`) — чистая экспонента выше, прогресс полёта. По нему
  засчитываются уровни и определяется момент краха;
- **эффективный** (`effective = base × boost_factor`) — то, что видит игрок и по
  чему считается выигрыш.

Без такого разделения сработавший бустер мгновенно «перепрыгивал» бы через
несколько уровней (коэффициент ведь скачком вырос), хотя физически шар их не
пролетал, и игрок получал бы очки за не пройденный путь. Крах поэтому
наступает при `base ≥ crash_point`, а в результат пишется
`crashAt = crash_point × boost_factor`.

## 3. Уровни (levels)

Уровень — это не точка во времени, а порог коэффициента. Массив
`level_thresholds` (длина 9 для зелёной темы, 12 для красной) задаёт, при каком
значении `multiplier(t)` засчитывается переход на очередной уровень. Такая
развязка позволяет менять визуальную "высоту" шара и физику полёта независимо
от игровой механики — и настраивается только правкой одного массива в конфиге.

Пороги растут не линейно, а с ускорением (по факту — геометрической прогрессией
с плюс-минус 15–25% шагом), чтобы соответствовать риск-профилю: ранние уровни
преодолеваются часто и легко, поздние — редко и с большим весом для решения
"забрать или рискнуть".

## 4. Позиция бустера

Если выбранная ставка включает бустер (`boost_tier > 1`), сервер перед стартом
раунда один раз разыгрывает **один** уровень, на котором появится бустер —
взвешенный случайный выбор по вероятностям `line_N_loot_prob` для текущей темы
(сумма вероятностей по всем уровням темы равна 1). Выбор фиксируется в момент
`round/start` вместе с `crash_point` и не меняется.

Если шар (по факту роста `multiplier(t)`) достигает уровня с бустером **раньше**
момента cashout — коэффициент умножается на `multiplier_tier_N_value`
(`N` = выбранный игроком tier: 2, 3 или 4), где сам бустер применяется один раз
за раунд. После cashout любое последующее достижение уровня бустера не
учитывается — визуально шар долетает до него, но эффект уже не применяется.

## 5. Автовывод

Игрок может до старта назвать коэффициент, на котором выигрыш зафиксируется сам
(`autoCashoutAt` в `POST /round/start`). Смысл механики не в удобстве, а в
психологии жанра: решение, принятое заранее и на холодную голову, защищает от
«ещё чуть-чуть», из-за которого ставка чаще всего и сгорает.

Проверка идёт на сервере в том же цикле тиков, **до** проверки краха: если порог
достигнут в том же тике, в котором наступает крах, выигрыш всё равно
фиксируется. Держать эту логику на клиенте нельзя — вывод зависел бы от лагов
вкладки и не срабатывал бы на свёрнутой странице.

Порог допустим от первого порога уровня до `max_multiplier`: ниже первого уровня
«Забрать» не работает по правилам игры, и автовывод молча никогда бы не сработал.

Сработать автовывод может выше названного порога: если бустер умножает
коэффициент одним скачком, сервер фиксирует первое значение после скачка.
Например, порог ×4.0 с бустером ×3 в замере дал фиксацию на ×7.55 — игрок
получает больше цели, а не меньше.

## 6. Выигрыш и очки

```
win_amount = bet * multiplier_at_cashout        // 0, если cashout не произошёл
points = points_per_line * levels_crossed
       + (points_cashout_bonus, если был cashout)
       + (points_boost_bonus, если сработал бустер)
```

Очки начисляются независимо от исхода раунда (в т.ч. при проигрыше — за уже
пройденные к моменту краха уровни), бонусные баллы — только при успешном
cashout.

## 7. Честность (provably fair, упрощённая схема)

1. Перед стартом раунда сервер генерирует `server_seed` (через `SecureRandom`,
   либо берёт его из dev-поля `seed`) и вычисляет по нему `crash_point` и
   позицию бустера.
2. Клиенту в ответе на `POST /api/round/start` отдаётся только
   `resultHash` — исход уже определён, но скрыт:

   ```
   resultHash = SHA256("<crash_point с 6 знаками>|<boost_level_index>|<server_seed>")
   ```

   Форматирование числа выполняется с `Locale.ROOT`: на русской локали `%.6f`
   дал бы `3,560465`, и хеш зависел бы от настроек машины, на которой запущен
   сервер.
3. После краха `GET /api/round/{id}` раскрывает `serverSeed`, `crashPointRaw`
   (те самые 6 знаков) и `boostLevelIndex`. Этого набора достаточно, чтобы
   пересчитать SHA-256 самому и убедиться, что опубликованный до полёта хеш
   совпадает — то есть сервер не подменил исход по факту действий игрока.
4. Проверить можно одной строкой, без нашего кода:

   ```bash
   node -e "console.log(require('crypto').createHash('sha256').update('3.560465|-1|42').digest('hex'))"
   ```

   Значение должно совпасть с `resultHash` из ответа. `boostLevelIndex = -1`
   означает, что бустер в раунде не разыгрывался.
5. Готовый JS-калькулятор хеша в интерфейсе игры — необязательное улучшение;
   для прототипа достаточно того, что данные раскрываются и алгоритм описан
   здесь.

## 8. Влияние параметров конфига — сводная таблица

| Параметр | Где влияет | Эффект при увеличении |
|---|---|---|
| `alpha` | точка краха | реже ранние крахи, "щедрее" игра |
| `max_multiplier` | точка краха | выше потолок редких больших "иксов" |
| `min_crash_multiplier` | точка краха | поднимает нижнюю границу краха |
| `multiplier_growth_rate` | начальная скорость роста | быстрее стартует, раунды короче |
| `growth_acceleration_base` | разгон полёта | сильнее ускорение к концу, хвост короче |
| `level_thresholds[]` | привязка уровней к коэффициенту | смещает, где засчитывается уровень |
| `line_N_loot_prob` | позиция бустера | чаще/реже бустер на конкретном уровне N |
| `multiplier_tier_N_value` | сила бустера | сильнее скачок коэффициента при срабатывании |
| `points_per_line` / `points_cashout_bonus` / `points_boost_bonus` | начисление очков | быстрее растёт счёт игрока |

Сценарий проверки 5 из ТЗ опирается именно на последнюю строку: эксперт меняет
`points_per_line` в конфиге, перезапускает раунд и видит новое начисление очков
за уровень без пересборки кода.

## 9. Замеренное поведение модели

Прогон `GET /api/dev/simulate?rounds=20000&theme=green` на текущих параметрах
(`alpha = 0.97`, `max_multiplier = 50`):

| Метрика | Значение |
|---|---|
| Средняя точка краха | 4.81 |
| Медианная точка краха | 1.94 |
| Доля раундов с крахом ниже ×2 | 51.5% |
| Доля раундов с крахом выше ×10 | 9.6% |
| Среднее число пройденных уровней (из 9) | 4.42 |

Медиана 1.94 совпадает с теоретической `alpha / (1 - 0.5) = 1.94` — модель
реализована в соответствии с формулой. Распределение тяжелохвостое: половина
раундов заканчивается до ×2 (создаёт напряжение и мотивирует забирать раньше),
но примерно каждый десятый раунд переваливает за ×10 (даёт те самые истории про
крупный выигрыш, ради которых игрок возвращается).

Проверять влияние параметров нужно именно таким прогоном, а не по исходу
одного случайного раунда — это прямо оговорено в ТЗ.
