# Контракт API — «Воздушный Шар»

Меняется только по согласованию обеих сторон (см. `CLAUDE.md`). Любое изменение —
отдельный коммит, сразу сказать напарнику.

Base URL: `http://localhost:8080/api`
WebSocket (STOMP over SockJS): `http://localhost:8080/ws`

## Аккаунты и сессия

Вход по логину и паролю. Сессия хранится в куке `JSESSIONID`
(`HttpOnly`, `SameSite=Lax`), пароли — bcrypt-хешем. `userId` в путях и телах
не передаётся: сервер берёт игрока из сессии, иначе чужим балансом можно было бы
играть, подставив идентификатор.

Все запросы ниже требуют сессии и отвечают `401 UNAUTHORIZED` без неё — по этому
ответу фронт понимает, что пора показать экран входа. Исключения:
`POST /api/auth/register` и `POST /api/auth/login`.

Роли: `PLAYER` и `ADMIN`. Только админу доступны `PUT /api/config`,
`/api/dev/**` и `/h2-console` — остальным `403 FORBIDDEN`.

Демо-аккаунты создаются при первом запуске из `config/accounts.json`
(логины и пароли — в README). Новый игрок получает баланс из `config/game.json`
→ `demo_user.starting_balance`.

Баланс можно пополнить до стартового в любой момент — `POST /api/demo/topup`.
Без этого проигранный в ноль баланс запирает игру, а ТЗ требует, чтобы эксперт
прошёл все сценарии без обращения к команде.

### `POST /api/auth/register`
```json
{ "username": "artyom", "password": "test123", "displayName": "Артём" }
```
`username` — латиница, цифры, `-`, `_`, от 3 до 20 символов, приводится к
нижнему регистру. `password` — от 6 символов. `displayName` необязателен, по
умолчанию равен логину. Регистрация сразу выполняет вход.

Response 200 — объект пользователя (см. ниже). Ошибки: `USERNAME_TAKEN` (409),
`VALIDATION_ERROR` (400).

### `POST /api/auth/login`
```json
{ "username": "player1", "password": "player123" }
```
Response 200 — объект пользователя. Ошибка: `INVALID_CREDENTIALS` (401).
Текст ошибки одинаков для неверного логина и неверного пароля, чтобы форма не
превращалась в способ проверять существование аккаунтов.

### `POST /api/auth/logout`
Гасит сессию. Response 200: `{ "ok": true }`.

### `GET /api/auth/me`
Текущий пользователь; `401`, если сессии нет.

```json
{
  "id": "c36ad74c-dd70-4c77-a8b8-942c20e6fe52",
  "username": "player1",
  "displayName": "Игрок 1",
  "role": "PLAYER",
  "balance": 1000,
  "totalPoints": 0
}
```

## Общий формат ошибки

```json
{ "error": "INSUFFICIENT_BALANCE", "message": "Не хватает бонусов" }
```

Коды: `INSUFFICIENT_BALANCE`, `INVALID_BET_OPTION`, `ROUND_NOT_ACTIVE`,
`ROUND_ALREADY_ACTIVE`, `ALREADY_CASHED_OUT`, `VALIDATION_ERROR`,
`UNAUTHORIZED` (401), `INVALID_CREDENTIALS` (401), `FORBIDDEN` (403),
`USERNAME_TAKEN` (409).

## REST-эндпоинты

### `GET /api/state`
Стартовое состояние при загрузке фронта.

Response 200:
```json
{
  "user": {
    "id": "c36ad74c-dd70-4c77-a8b8-942c20e6fe52",
    "username": "player1",
    "displayName": "Игрок 1",
    "role": "PLAYER",
    "balance": 1000,
    "totalPoints": 0
  },
  "balance": 1000,
  "theme": "green",
  "activeRound": null,
  "stake": { "min": 10, "max": 400, "step": 5, "presets": [25, 50, 100, 200] },
  "boostOptions": [
    { "id": "no-boost", "boostTier": 1, "priceFactor": 0.0, "boostMultiplier": 1 },
    { "id": "boost-x2", "boostTier": 2, "priceFactor": 0.5, "boostMultiplier": 2 },
    { "id": "boost-x3", "boostTier": 3, "priceFactor": 1.0, "boostMultiplier": 3 },
    { "id": "boost-x4", "boostTier": 4, "priceFactor": 1.5, "boostMultiplier": 4 }
  ],
  "levelsCount": { "green": 9, "red": 12 }
}
```

**Ставка и цена бустера.** Сумму ставки игрок задаёт сам в границах `stake`.
Бустер — отдельная покупка, и цена у него не фиксированная, а доля от ставки:

```
доплата = ceil(ставка × priceFactor)
списывается = ставка + доплата
выигрыш     = ставка × коэффициент        // доплата в выплате не участвует
```

Клиент считает доплату для подсказки, но источник правды — сервер: он
пересчитывает её при старте раунда. Обоснование цен — в `docs/math-model.md`,
раздел 4.

Если `activeRound` не null — фронт восстанавливает незавершённый раунд (перезагрузка
страницы) и подписывается на его WebSocket-топик. Набор полей внутри `activeRound`
тот же, что отдаёт `POST /api/round/start` (`roundId`, `theme`, `stake`,
`boostFee`, `totalPaid`, `boostMultiplier`, `levelsCount`, `levelThresholds`,
`boostLevelIndex`, `resultHash`), плюс текущее состояние полёта: `multiplier`,
`levelsCrossed`, `boostApplied`, `points`, `elapsedMs`, `autoCashoutAt`,
`cashedOutAt`, `winAmount`.

### `GET /api/rules`
Текст правил игры (см. `docs/rules.md` — источник контента). Отдаёт готовый HTML/markdown
блок, чтобы не дублировать текст на фронте и бэке.

Response 200:
```json
{ "content": "## Как играть\n\n..." }
```

### `POST /api/demo/topup`
Пополняет баланс демо-игрока **до** стартового значения (`demo_user.starting_balance`).
Тела запроса нет.

Response 200:
```json
{ "credited": 850, "balance": 1000 }
```

`credited` — сколько реально начислено. Если баланс уже не ниже стартового,
возвращается `{ "credited": 0 }` и баланс не меняется: пополнение восстанавливает
счёт, но не позволяет накрутить его выше исходного.

Фронт показывает кнопку «Пополнить», как только баланс упал ниже стартового, и
отдельную плашку, когда не хватает даже на самую дешёвую ставку.

### `POST /api/round/start`
Списывает ставку с доплатой за бустер, сервер уже вычислил (но не раскрыл) точку
краха и позицию бустера, создаёт раунд, возвращает его id и provably-fair хеш.

Request:
```json
{ "theme": "green", "stake": 150, "boostOptionId": "boost-x2" }
```

`stake` — сумма ставки в баллах, свободная в границах `stake.min … stake.max` и
кратная `stake.step`. Нарушение любого из трёх условий → `VALIDATION_ERROR` с
текстом, который можно показать игроку как есть.

Опциональное поле `autoCashoutAt` (number) — коэффициент, на котором сервер сам
зафиксирует выигрыш. Допустимо от первого порога уровня до `max_multiplier`;
ниже первого уровня «Забрать» не работает по правилам игры, и автовывод молча
никогда бы не сработал. `null` или отсутствие поля — автовывод выключен.

Опциональные dev-поля (см. раздел «Dev-режим»): `seed`, `speedFactor`.

Response 200:
```json
{
  "roundId": "r-103",
  "theme": "green",
  "stake": 150,
  "boostFee": 75,
  "totalPaid": 225,
  "boostMultiplier": 2,
  "levelsCount": 9,
  "levelThresholds": [1.10, 1.25, 1.45, 1.70, 2.00, 2.50, 3.20, 4.50, 7.00],
  "boostLevelIndex": 5,
  "autoCashoutAt": null,
  "resultHash": "3f9c2a...e1",
  "balanceAfter": 775
}
```

`stake` / `boostFee` / `totalPaid` — ставка, доплата за бустер и общая сумма
списания. Выигрыш считается **только от `stake`**: доплата сгорает в любом
случае, и именно это делает бустер осмысленной покупкой, а не бесплатной
добавкой (разбор в `docs/math-model.md`, раздел 4).

`boostLevelIndex` — уровень, на котором ждёт бустер (`-1`, если ставка без
бустера). Раскрывается сразу, до полёта: ТЗ описывает механику «игрок может
сознательно ждать уровня с бустером, рискуя крахом», а ждать невидимый маркер
невозможно. Точку краха это не выдаёт — она остаётся закрытой в `resultHash`.
`levelThresholds` — коэффициенты, при пересечении которых засчитывается переход на
следующий уровень (длина = `levelsCount`). `resultHash` — sha256 от
`(crashPoint, boostLevelIndex, serverSeed)`, публикуется ДО полёта; серверный seed
раскрывается только на `GET /api/round/{roundId}` после завершения раунда — для
проверки честности.

Ошибки: `INSUFFICIENT_BALANCE` (баланса не хватает на `totalPaid`),
`INVALID_BET_OPTION` (нет такого варианта бустера), `VALIDATION_ERROR`
(ставка вне границ или не по шагу).

Сразу после успешного ответа фронт подписывается на WebSocket-топик
`/topic/round/{roundId}` и получает поток тиков коэффициента (см. ниже).

### `POST /api/round/{roundId}/cashout`
Фиксирует выигрыш по текущему коэффициенту. Коэффициент на момент нажатия
пересчитывается и валидируется на сервере по времени старта раунда — клиентское
значение коэффициента не принимается как аргумент.

Response 200:
```json
{
  "roundId": "r-103",
  "cashedOutAt": 2.35,
  "winAmount": 352,
  "pointsSoFar": 180
}
```
Ошибки: `ROUND_NOT_ACTIVE` (раунд уже завершён crash-ом), `ALREADY_CASHED_OUT`.

Раунд после этого продолжает жить до фактического crash — `winAmount` уже
зафиксирован и не меняется, шар долетает визуально по тем же WS-событиям.

### `GET /api/round/{roundId}`
Итог завершённого раунда (после события `round.finished` по WS) — экран
результата запрашивает эту ручку, чтобы не терять данные при разрыве соединения.

Response 200:
```json
{
  "roundId": "r-103",
  "theme": "green",
  "stake": 150,
  "boostFee": 75,
  "totalPaid": 225,
  "outcome": "cashout",
  "cashedOutAt": 2.35,
  "crashAt": 3.10,
  "winAmount": 352,
  "points": 278,
  "reward": { "type": "puzzle-piece", "id": "green-7" },
  "balance": 1046,
  "resultHash": "3f9c2a...e1",
  "serverSeed": "42",
  "crashPointRaw": "3.560465",
  "boostLevelIndex": -1
}
```
`outcome`: `cashout` | `crash`. При `crash` — `winAmount: 0`, `cashedOutAt: null`,
`reward` заполняется по тем же правилам (награда даётся всегда, не только при
выигрыше).

Последние четыре поля — для проверки честности. `crashAt` округлён до 2 знаков и
потому для сверки хеша не годится, а позиция бустера иначе вообще не
раскрывается; без них пересчитать `resultHash` невозможно. Проверка:

```
sha256("<crashPointRaw>|<boostLevelIndex>|<serverSeed>") === resultHash
sha256("3.560465|-1|42") === "7ecdc7ce..."
```

`boostLevelIndex` равен `-1`, если бустер в раунде не разыгрывался.

### `GET /api/config`
Текущая игровая конфигурация (для админки — доп. модуль). Отдаёт содержимое
`config/game.json` как есть.

### `PUT /api/config`
Сохранение настроек из админ-панели. Тело — полный JSON конфигурации в том же
формате, что отдаёт `GET /api/config`.

Записывается ровно присланный текст (после проверки), поэтому поля, которых нет
в модели сервера — например пояснение в `dev_mode._comment` — не теряются.
Пишем во временный файл и переименовываем: оборванная запись не оставит
обрубок, на котором игра развалится.

Значения проверяются на сервере, клиент не может быть единственным местом, где
живут допустимые диапазоны:

| Параметр | Допустимо |
|---|---|
| `alpha` | 0.01 … 1.0 |
| `max_multiplier` | 1.1 … 1000 |
| `min_crash_multiplier` | 1.0 … `max_multiplier` |
| `multiplier_growth_rate` | 0.01 … 5.0 |
| `delta` | 0.02 … 1.0 |
| `points.*`, `starting_balance` | не отрицательные |
| `multiplier_tier_N_value` | 1 … 100 |
| `level_thresholds` | строго возрастают, первый > 1.0, длина = `levels_count` |
| `bet_options[].cost` | больше нуля |
| `loot_probabilities` | не отрицательные, сумма больше нуля |

Ошибка приходит как `VALIDATION_ERROR` с текстом, называющим конкретное поле —
он показывается администратору как есть:

```json
{ "error": "VALIDATION_ERROR", "message": "green: levels_count (7) не совпадает с числом порогов (9)" }
```

Изменения применяются со следующего раунда, без перезапуска сервера.

### `GET /api/leaderboard`
Первый снимок турнирной таблицы; дальше она приходит по `/topic/leaderboard`.
Формат строк — там же.

### `GET /api/admin/report` — только роль `ADMIN`
Сводная отчётность: считается на лету из таблицы раундов, отдельного хранилища
агрегатов нет — оно разошлось бы с исходными данными.

Блоки ответа:

| Поле | Что внутри |
|---|---|
| `totals` | раунды, аккаунты, принято ставок, выплачено, маржа, RTP, очки, доли выводов и крахов, средний/медианный/максимальный крах |
| `crashDistribution` | корзины точки краха (`from`, `to`, `count`, `share`); разбиение неравномерное, потому что половина раундов заканчивается ниже 2.0 |
| `boostTiers` | по каждому тиру: сколько раз куплен, сколько раз успел сработать, собрано доплат, выплачено |
| `themes` | раунды, оборот и возврат по каждой теме |
| `players` | баланс, очки, раунды, потрачено, выиграно, итог, лучший вывод |
| `recent` | последние 25 раундов с исходом, коэффициентом и судьбой бустера |

`rtp` = `paidOut ÷ totalPaid`, где `totalPaid` включает доплату за бустер: она
сгорает всегда и в выплате не участвует, поэтому обязана быть в знаменателе.

## WebSocket (STOMP)

Подключение: `SockJS` на `/ws`, дальше STOMP `CONNECT`. Требует сессии —
анонимный handshake получает `401`.

Соединение поднимается **один раз после входа** и живёт всю сессию. Раньше оно
создавалось на каждый раунд, и короткий раунд (шар лопается на 1.00 за десяток
миллисекунд) заканчивался раньше, чем оформлялась подписка: клиент не получал
ни одного события и оставался в бесконечном полёте.

### Подписка: `/topic/round/{roundId}`

События, `type` — дискриминатор:

**`tick`** — обновление коэффициента, ~10 раз/сек, пока раунд активен:
```json
{ "type": "tick", "multiplier": 1.42, "elapsedMs": 820 }
```

**`level`** — пересечён уровень (индекс с 0):
```json
{ "type": "level", "levelIndex": 2, "pointsAwarded": 10, "totalPoints": 30 }
```

**`boost`** — шар долетел до уровня с бустером (только если cashout ещё не было):
```json
{ "type": "boost", "levelIndex": 5, "boostMultiplier": 2, "multiplierAfter": 4.20 }
```

**`cashout`** — выигрыш зафиксирован:
```json
{ "type": "cashout", "multiplier": 2.35, "winAmount": 352, "points": 180, "auto": true }
```
`auto: true` — сработал автовывод, `false` — игрок нажал «Забрать». Событие
приходит в обоих случаях, чтобы состояние раунда было одинаковым независимо от
того, кто его зафиксировал. При ручном выводе клиент уже знает результат из
ответа REST и может это событие проигнорировать.

Автовывод может сработать выше заданного порога: если бустер умножает
коэффициент одним скачком, сервер фиксирует первое значение после скачка.
Игрок при этом получает больше цели, а не меньше.

**`round.finished`** — крах, раунд завершён:
```json
{
  "type": "round.finished",
  "crashAt": 3.10,
  "outcome": "cashout",
  "winAmount": 352,
  "points": 278,
  "serverSeed": "8b7a..."
}
```
После этого события фронт отписывается от топика и запрашивает
`GET /api/round/{roundId}` для итогового экрана.

### Подписка: `/topic/leaderboard` — живой рейтинг

Турнирная таблица всех участников. Соперники настоящие: это те же аккаунты,
что играют в прототипе, никакой имитации на клиенте больше нет.

Рассылается при каждом изменении очков — пересечение уровня, срабатывание
бустера, фиксация выигрыша, завершение раунда. Поэтому позиция меняется прямо
во время полёта, как требует §1.6 ТЗ, а не после краха.

```json
{
  "rows": [
    { "playerId": "c36ad74c-…", "name": "Игрок 1", "points": 540, "inFlight": true, "place": 1 },
    { "playerId": "a7769c10-…", "name": "Крупный игрок", "points": 270, "inFlight": false, "place": 2 }
  ]
}
```

`points` — накопленные очки аккаунта **плюс** набранные в незавершённом раунде;
`inFlight` — игрок сейчас в воздухе, его очки ещё растут. Первый снимок берётся
из `GET /api/leaderboard`, дальше таблица приходит сама.

Имена отдаются полностью, деперсонализация (`***`) делается в интерфейсе — ТЗ
допускает это для прототипа.

### Подписка: `/topic/feed` — лента завершённых раундов

Раунд любого участника, который только что закончился. Нужна, чтобы общая
история игр на экране ставки обновлялась без перезагрузки страницы.

```json
{
  "roundId": "r-42",
  "player": "Игрок 1",
  "theme": "green",
  "stake": 50,
  "outcome": "crash",
  "multiplier": 1.35,
  "winAmount": 0,
  "points": 30
}
```

## Dev-режим (воспроизводимость случайных событий)

Механика построена на случайности, а случайность невозможно отлаживать: чтобы
проверить экран бустера или ранний крах, иначе пришлось бы переигрывать раунды,
пока нужный исход не выпадет сам. ТЗ прямо рекомендует режим разработчика с
фиксированным seed (п. 2.3) — он же позволяет показать бустер на демонстрации
экспертам, не полагаясь на удачу.

Включается флагом `dev_mode.enabled` в `config/game.json`. **Если dev-режим
выключен, сервер обязан игнорировать все поля ниже** — иначе клиент сможет
влиять на исход, что прямо запрещено требованием честности.

### Дополнительные поля `POST /api/round/start`

```json
{
  "theme": "green",
  "stake": 150,
  "boostOptionId": "boost-x2",
  "seed": 42,
  "speedFactor": 5
}
```

- `seed` (int, опционально) — фиксирует `server_seed`, а значит и точку краха, и
  позицию бустера. Один и тот же `seed` + одна и та же тема + один и тот же
  `boostOptionId` = полностью идентичный раунд.
- `speedFactor` (number, опционально, по умолчанию `1`) — множитель скорости
  роста коэффициента. `5` означает, что раунд проходит в 5 раз быстрее: удобно,
  когда проверяешь экран результата в двадцатый раз подряд. На саму математику
  (какой коэффициент в какой момент полёта) не влияет — меняется только темп.

### Согласованные seed для проверки сценариев

Чтобы обе половины команды проверяли одно и то же, договариваемся о наборе seed
и записываем сюда фактические значения, как только backend заработает:

Значения ниже замерены прогоном и детерминированы — тот же seed всегда даёт тот
же раунд:

| seed | Тема | Ставка | Крах | Бустер | Для чего |
|---|---|---|---|---|---|
| 3 | red | boost-x3 | ×1.09 | уровень 9 | сценарий 3: крах почти сразу, «Забрать» не успеть |
| 7 | green | no-boost | ×1.59 | — | короткий раунд, cashout возможен |
| 1 | green | no-boost | ×2.24 | — | спокойный средний полёт |
| 2 | green | boost-x2 | ×2.37 | уровень 7 | бустер не успевает сработать до краха |
| 42 | green | boost-x2 | ×7.51 | уровень 3 | сценарий 4: бустер срабатывает и удваивает коэффициент |
| 23 | green | no-boost | ×10.72 | — | сценарий 2: длинный полёт, спокойно забрать на ×2.5 |

Крах указан итоговый — для раундов с сработавшим бустером он уже умножен.

**Важно:** seed прогоняется через `SplittableRandom` (SplitMix64), а не через
`java.util.Random`. У последнего линейный конгруэнтный генератор слабо
перемешивает малые seed: для 1, 2, 3, 7, 42 первый `nextDouble()` попадает в
диапазон 0.722–0.732, то есть все раунды получали практически одинаковую точку
краха (~3.6), и режим воспроизводимости не давал ничего, кроме иллюзии.

### `GET /api/dev/simulate?rounds=10000` (опционально, для документации)

Прогоняет N раундов без записи в БД и возвращает статистику распределения точки
краха — нужно, чтобы обосновать мат. модель в документации расчётами, а не
исходом одного случайного раунда (прямое требование ТЗ к сценарию 5).

Реальный ответ на текущих параметрах конфига (не выдуманный пример — эти числа
замерены прогоном, см. `docs/math-model.md`):

```json
{
  "rounds": 50000,
  "theme": "green",
  "meanCrash": 4.812,
  "medianCrash": 1.932,
  "crashBelow2Pct": 51.75,
  "crashAbove10Pct": 9.754,
  "maxCrash": 50.0,
  "levelsReachedAvg": 4.426
}
```

## Договорённости по типам данных

- Все денежные/очковые величины — целые числа (`int`), баллы не дробные.
- Коэффициенты (`multiplier`, `crashAt`, `levelThresholds`) — `number`, 2 знака
  после запятой на отображении, на бэке храним с большей точностью.
- Время — ISO 8601 UTC (`2026-09-11T10:22:31Z`).
- `theme`: строковый enum `"green" | "red"`, никаких магических чисел на фронте.
