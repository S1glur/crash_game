# Воздушный Шар

Бонусная crash-игра с турнирной механикой — кейсовое задание Чемпионата России по
продуктовому программированию, ФСП, онлайн-этап 11–13 сентября 2026.

Игрок ставит бонусные баллы и старается забрать растущий выигрыш до того, как
воздушный шар лопнет (crash-механика). Подробности — в `docs/zadacha-razbor.md`.

## Что реализовано

Обязательные сценарии проверки 1–5 работают целиком.

1. **Экран ставки.** Свободная сумма с пресетами и ползунком, четыре варианта
   бустера с ценой в долях ставки, общая история завершённых полётов всех
   игроков, правила и обучение доступны до подтверждения ставки, переключение
   тем (Изумруд — 9 уровней, Бордо — 12).
2. **Полёт.** Коэффициент считает сервер и рассылает десять раз в секунду,
   очки за пройденные уровни, «Забрать» открывается после первого уровня,
   подсказка при первом полёте.
3. **Вывод и крах.** Выигрыш по зафиксированному коэффициенту, «могли бы
   забрать больше», шар долетает до настоящей точки краха, экран результата
   открывается только после неё.
4. **Бустер.** Уровень разыгрывает сервер до взлёта по вероятностям темы,
   маркер виден только в полёте, срабатывание умножает личную выплату и даёт
   дополнительные очки.
5. **Параметры без релиза.** Админ-панель и `config/game.json` с hot-reload:
   правка применяется со следующего раунда и расходится всем клиентам по
   WebSocket, без перезагрузки страницы.

Сверх обязательного минимума:

- отдельный экран выбора темы;
- живой турнир — таблица пересобирается на сервере и меняется прямо в полёте;
- таблица участников и лента завершённых раундов;
- апсейл «Закрепи успех» после крупного выигрыша, не чаще раза за сессию;
- автовывод на стороне сервера — срабатывает даже со свёрнутой вкладкой;
- проверяемая честность раунда с пересчётом хеша прямо в интерфейсе;
- отчётность администратора с выгрузкой журнала полётов в CSV;
- обучение из шести шагов, звуковое сопровождение, адаптив 320–1920.

## Ограничения прототипа

- Один процесс: раунды, брокер сообщений и сессии живут в памяти, поэтому
  горизонтальное масштабирование требует внешнего брокера и ведущего узла.
- Нагрузка проверена до 30 одновременных игроков: около 4 % одного ядра и
  316 МБ памяти при ровном ритме в 10 тиков в секунду.
- На бесплатном тарифе Render сервис засыпает после 15 минут простоя —
  первый заход после сна ждёт холодный старт около минуты.
- `dev_mode` в конфиге включён: он открывает администратору прогон
  математической модели сериями (`GET /api/dev/simulate`).

## Стек

- **Backend:** Java 21, Spring Boot 4.1, Spring Security (сессия + BCrypt),
  WebSocket (STOMP over SockJS), JPA
- **Frontend:** React 19, TypeScript, Vite, zustand; графика — SVG и CSS
- **Данные:** H2 (файловая) локально, PostgreSQL на хостинге
- **Поставка:** один jar с фронтендом внутри, Dockerfile, автодеплой из `main`
- **Конфигурация:** `config/game.json` (hot-reload, без пересборки кода),
  `config/accounts.json` (демо-аккаунты)

## Запуск

Требуется **JDK 21+** (Spring Boot 4 не работает на Java 17 и ниже).
Проверить: `java -version`. Установить: `winget install EclipseAdoptium.Temurin.21.JDK`.

### Вариант 1 — одной командой (для проверки)

```bash
cd backend
./mvnw -Pprod clean package -DskipTests
java -jar target/balloon-0.0.1-SNAPSHOT.jar
```

Игра целиком открывается на **http://localhost:8080** — фронтенд собран внутрь
артефакта, отдельный сервер поднимать не нужно. Node на машине не требуется:
профиль `prod` скачивает его сам на время сборки.

Jar можно перенести в любую папку и запустить оттуда: если рядом нет
`config/game.json`, приложение развернёт эталонный конфиг при старте — и его
по-прежнему можно править на ходу (сценарий 5 работает и в таком запуске).

### Вариант 2 — для разработки (два процесса)

Нужен, когда правишь фронтенд: Vite пересобирает изменения на лету.

```bash
# терминал 1 — бэкенд
cd backend
./mvnw spring-boot:run

# терминал 2 — фронтенд
cd frontend
npm install
npm run dev
```

Открывать **http://localhost:5173** — Vite проксирует `/api` и `/ws` на 8080,
поэтому фронт везде ходит относительными путями и в проде ничего менять не надо.

При запуске через `mvnw spring-boot:run` рабочая папка — `backend/`, пути к
`config/game.json` и `docs/rules.md` в `application.properties` заданы
относительно неё.

### Вариант 3 — развернуть на Render

В репозитории лежит `render.yaml`: Render читает его сам и создаёт веб-сервис
вместе с базой. В панели: **New → Blueprint**, указать этот репозиторий,
подтвердить. Дальше каждый пуш в `main` пересобирает и выкатывает сайт
автоматически.

Собирается всё из `Dockerfile` — нативной среды для Java у Render нет. Внутри
контейнера выполняется тот же `mvnw -Pprod package`, что и локально: фронтенд
уезжает внутрь jar, наружу торчит один порт.

Про базу: адрес приходит переменной `DATABASE_URL`, а `docker-entrypoint.sh`
превращает её в JDBC-адрес с логином и паролем — руками в панели ничего
разносить не нужно. Если базу не подключать, прототип всё равно поднимется на
файловой H2, но данные будут пропадать при каждом деплое: диск там эфемерный.

Что нужно знать про бесплатный тариф:

- **Сервис засыпает** после 15 минут без входящих запросов. Внутренний цикл
  раундов активностью не считается, так что перед показом сайт надо разбудить
  заранее: первый заход после сна ждёт холодный старт около минуты.
- **Инстанс должен быть один.** Раунды, брокер сообщений и сессии живут в
  памяти процесса — второй экземпляр начал бы крутить свои раунды, и люди на
  одном адресе видели бы разные шары.
- **Бесплатная база живёт ограниченный срок** и потом удаляется. Для
  хакатона этого хватает, для жизни после — нет.

Проверено нагрузкой: 30 одновременных игроков сервер держит, тратя около 4 %
одного ядра и 316 МБ памяти, с ровным ритмом в 10 тиков в секунду.

### Адреса бэкенда

| URL | Что это |
|---|---|
| `/api/...` | REST API (контракт — `docs/api.md`) |
| `/ws` | WebSocket STOMP (тики коэффициента) |
| `/ws-test.html` | Проверка игрового цикла без фронтенда |
| `/h2-console` | Консоль БД (`jdbc:h2:file:./data/balloon`, логин `sa`, пароль пустой) — только для роли админа |

### Проверка бэкенда без фронтенда

- **`/ws-test.html`** — выбрать тему и ставку, нажать «Начать раунд»: видно поток
  тиков, пересечение уровней, срабатывание бустера и крах. Поля `seed` и `speed`
  воспроизводят один и тот же раунд и ускоряют полёт.
- **`docs/api.http`** — все запросы контракта для расширения REST Client в VS Code.

## Демо-доступ

Игра открывается экраном входа. Аккаунты ниже создаются автоматически при первом
запуске сервера — на экране входа они перечислены, и по клику логин с паролем
подставляются в форму, вводить вручную не нужно.

| Логин | Пароль | Роль | Баланс | Для чего |
|---|---|---|---|---|
| `admin` | `admin123` | админ | 100 000 | настройка параметров игры (сценарий 5) |
| `vip` | `vip12345` | игрок | 50 000 | крупные ставки без оглядки на баланс |
| `player1` | `player123` | игрок | 1 000 | обычный игрок |
| `player2` | `player123` | игрок | 1 000 | второй игрок — видно, что балансы и история раздельные |

Можно и зарегистрировать свой аккаунт: логин латиницей от 3 до 20 символов,
пароль от 6. Новый игрок получает баланс из `config/game.json`
(`demo_user.starting_balance`, по умолчанию 1000 бонусных баллов).

Список аккаунтов задаётся в `config/accounts.json`. Файл отдельный от
`game.json` намеренно: `game.json` целиком отдаётся клиенту через
`GET /api/config`, и пароли уехали бы вместе с ним. Уже существующие аккаунты
сидер не трогает — чтобы смена пароля не откатывалась при перезапуске.

Что закрыто ролью администратора: `PUT /api/config` (правка экономики),
`GET /api/admin/report` (отчётность), `/api/dev/**` (прогон мат. модели) и
`/h2-console`. Игрок получит на них 403, а кнопки в углу экрана ему просто
не показываются.

## Честная игра

Точка краха и уровень бустера разыгрываются при создании раунда, до приёма
ставок публикуется `SHA-256(точка краха | уровень бустера | seed)`. После
краха сервер раскрывает саму строку — и это можно проверить, не веря нам на
слово: в игре отпечаток кликабельный, открывается разбор со строкой раунда,
пересчётом SHA-256 прямо на странице и готовой командой для PowerShell или
Node. Алгоритм и вывод формул — в `docs/math-model.md`.

## Турнир и отчётность

**Живой рейтинг.** Соперники настоящие — это те же аккаунты, что играют в
прототипе. Сервер пересобирает таблицу и рассылает её по `/topic/leaderboard`
при каждом изменении очков, поэтому позиция игрока меняется прямо во время
полёта. Очки складываются из накопленных в аккаунте и набранных в ещё не
завершённом раунде. Чтобы увидеть это вживую, откройте игру в двух браузерах
под `player1` и `player2` — строка турнира над сценой обновится у обоих.

**Лента.** Завершённый раунд любого участника уходит в `/topic/feed`, и общая
история игр на экране ставки обновляется без перезагрузки страницы.

**Отчётность.** Под `admin` в правом нижнем углу появляется кнопка с
диаграммой — отдельный экран, отвечающий на два вопроса: сколько игра
заработала и что происходило в последних раундах. Сверху четыре числа: прибыль
игры со знаком, возврат игроку, сколько было полётов и сколько игроков. Слева
приход и расход — ставки, доплата за бустеры, выплаты. Справа последние раунды
и кнопка выгрузки журнала в CSV для Excel.

Счётчики хода игры считаются по полётам, а не по ставкам: раунд с тремя
участниками состоялся один раз, а раунд, в котором никто не играл, всё равно
состоялся — цикл идёт непрерывно.

Данные лежат в файловой H2 (`backend/data/balloon.mv.db`) и переживают
перезапуск сервера. Чтобы начать с чистого листа — остановите сервер и удалите
этот файл: демо-аккаунты создадутся заново.

## Настройка параметров без пересборки

Правится `config/game.json` — файл перечитывается на старте каждого раунда,
перезапуск не нужен. Назначение параметров и их влияние на игру описаны в
`docs/math-model.md`.

Пример проверки (обязательный сценарий 5): поменять `points.points_per_line`
с 10 на 50, сохранить файл, начать новый раунд — за каждый пройденный уровень
начислится 50 очков вместо 10.
